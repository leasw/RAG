# 설계 근거 정리 (PPT 원본 문서)

## 1. MTM → LTM 승급 방식

### 정의
MTM 사실 중 3개 기준(AND)을 전부 통과해야 LTM으로 승격된다.

- **출처(traceable)**: `source_id`가 실제 원문 로그 파일(`data/raw/{chat,ai_chat}/*.jsonl`)로 이어지는가 — 데이터로 확인(결정적)
- **진실성(truthful)**: 구체적·검증 가능한 서술인가 — LLM 판정, 문서 근거(RRF 상위 스니펫)를 힌트로 줌
- **유용성(useful)**: 앞으로도 반복 참조될 가치가 있는가 — LLM 판정

셋 다 True여야 승격, 하나라도 실패하면 MTM에 남는다. (`org_agent_mvp/memory_promote.py:434` `_LTM_JUDGE_PROMPT`, `:492` `promote_to_ltm()`)

### 승격 후 처리 — 기존 LTM과의 대조
3개 기준을 통과한 후보라도 그대로 새 레코드로 쌓지 않는다. **이번에 새로 승격되는 후보끼리 병합하는 게 아니라, 각 후보를 기존 LTM과 1:1로 대조**한다.

```
후보(3기준 통과) → 기존 LTM 전체와 비교
   코사인 < 0.65                         무관한 사안 → 그대로 신규 승격
   코사인 >= 0.65, 상호함의 >= 2.0        같은 사실 → 중복, 후보 폐기 (기존 LTM 안 건드림)
   코사인 >= 0.65, 상호함의 [-6.0, 2.0)   같은 사안·다른 정보 → 기존 LTM 레코드 갱신
   코사인 >= 0.65, 상호함의 < -6.0        표면 단어만 겹친 무관한 문장 → 신규 승격
```

(`org_agent_mvp/memory_promote.py:267` `_resolve_against_ltm()`)

### 근거 — 왜 이 방식인가
- 기존 흡수 병합(absorb) 방식은 리랭커 오판 시 **이미 검증된 기존 LTM 레코드가 통째로 지워질 위험**이 있었다 → 기존 레코드를 지우거나 흡수하는 경로 자체를 없앰
- `UPDATE_FLOOR=-6.0` 하한은 실측으로 보정: 코사인 0.85로 겹쳤지만 상호함의 -7.65(완전 무관, "담당자 변경" vs "전담기관명")로 나온 실패 사례를 통해 도입 — 코사인만으로 "같은 사안"을 판단하면 안 된다는 걸 실측으로 확인
- 정정 사례의 실측 상호함의는 -1.34 ~ -4.16, 완전 무관은 -11.04 — 그 사이인 -6.0을 경계로 둠

### 알려진 한계
`truthful`/`useful` LLM 판정을 검증할 사람 라벨·사후 재참조 추적 정답셋이 없다 — 운영 시작점이지 확정값은 아니다.

## 2. 문서 코퍼스 입력 시 처리 분기

문서 하나가 파이프라인에 들어올 때, 여러 단계에서 조건부로 갈라진다 (`doc_rag/ingest.py:148` `ingest()`).

```
파일 1건
  │
  ├─ 확장자가 SUPPORTED_EXTS 밖 → skip(unsupported/unknown)
  ├─ 파일 크기 > max_file_mb(120MB) → skip(too_large)
  ├─ 캐시 일치(status=ok/skipped & mtime 동일, --force 아님) → skip(cached, 재처리 안 함)
  ├─ 같은 SHA256 해시의 문서가 이미 있음 → skip(duplicate_of, 사본 재적재 방지)
  │
  ▼ 여기까지 통과한 파일만 실제 변환 시도
  1차: docling-parse 백엔드로 변환
     │ 실패(PDF만 해당)
     ▼
  2차: pypdfium 백엔드로 재시도 (관대한 파서, 표 인식 품질은 낮음)
     │ 그래도 청크가 0개(텍스트 레이어 없는 스캔 PDF)
     ▼
  3차: EasyOCR 변환기로 재시도 (한/영, GPU, 이 단계에서만 OCR 비용 지불)
  │
  ▼
  형식별 청킹 파라미터 적용 (by_format: pdf/hwp/docx/pptx/xlsx/txt마다
  max_tokens·overlap_tokens 다름 — 예: pptx는 320/32로 짧게, hwp는 640/80으로 길게)
```

### 근거
- 3단 폴백은 실측 기반: 이 코퍼스 PDF 552개 중 306개가 텍스트 레이어 없는 스캔본이라, 처음부터 전부 OCR을 돌리면 느리고(텍스트 레이어 있는 문서엔 OCR이 오히려 품질 저하) 낭비가 큼 → "실패했을 때만" 다음 단계로 넘어가는 지연 생성(lazy) 구조
- OCR 단계에서는 표 구조 인식을 끔(`do_table_structure=False`) — 실측으로 OCR 결과에 표 모델을 얹으면 "평가구분, 1 = [단계평가..." 같은 깨진 셀이 나오는 걸 확인, 스캔 페이지는 줄 단위 평문이 검색 품질이 더 나음
- 형식별 청킹 크기 차등: pptx(슬라이드, 짧고 조각난 텍스트) vs hwp(서술형 긴 문단) vs xlsx(표, 행 경계에서만 자름 — overlap 0)

## 3. 지식그래프 검색 성능 개선 (엔티티 해소)

### 문제
그래프는 닫힌 어휘(schema.py에 정의된 개체만 인식)라, 질의문 표기가 등록된 정식 명칭과 정확히 일치하지 않으면(축약형 등) 아예 개체를 못 찾았다. 예: 질의 "경북대산학협력단" vs 등록 명칭 "경북대학교 산학협력단".

### 개선
정확 일치를 먼저 시도하고, 실패했을 때만 문자 단위 퍼지 매칭으로 한 번 더 시도 (`graph_rag/query.py:86` `resolve()`).

```
질의문
  │
  ├─ 표기 완전일치 시도 (긴 표기부터, 빠르고 오탐 없음)
  │     찾음 → 그대로 반환 (퍼지 매칭 안 돎 — 중복 계산 방지)
  │
  └─ 못 찾음 → 퍼지 매칭 폴백
        각 개체 표기와 길이가 비슷한 질의문 부분 문자열을 전부 비교
        (difflib.SequenceMatcher) → 개체별 최고 점수가 0.65 이상이면 채택
```

### 근거 — 왜 0.65인가, 왜 임베딩이 아니라 문자 매칭인가
- 의미 유사도(질의 임베딩 vs 개체 centroid)도 시도했으나, 이 코퍼스가 단일 프로젝트 문서 뭉치라 모든 개체의 centroid가 서로 비슷하게 뭉쳐 변별력이 없었음(정답·오답 코사인 차이 0.001~0.1) → 폐기
- 문자 단위 퍼지 매칭은 실측에서 뚜렷하게 갈림: 개체가 실제 언급된 질의는 0.800~1.000, 언급 없는 질의는 0.333~0.400
- 문턱을 0.6으로 두면 "경북대산학협력단" 질의에서 정답(경북대 0.800) 외에 가천대·동국대 산협까지 0.600으로 나란히 걸려 오답이 같이 채택됨(동률 구간) → 그 구간을 피해 0.65로 설정

## 4. 임베딩/리랭커 모델 메모리 탑재·재사용

### 정의
STM/MTM/LTM(FactMemory), doc_rag(DocRetriever), graph_rag(GraphRetriever·build), AgentRuntime의 기여도 계산까지 — 이 다섯 호출부가 전부 **같은 `doc_rag.embedding_factory.build_embedder()`를 거쳐 같은 설정(backend·model id·device·batch_size·max_seq_length)이면 이미 로드된 하나의 인스턴스를 공유**한다.

```
FactMemory(_vectors)  ──┐
DocRetriever          ──┤
GraphRetriever(query)  ──┼──▶ embedding_factory.build_embedder(cfg)
GraphRetriever(build)  ──┤        _INSTANCES[key] 캐시 조회
AgentRuntime(기여도)    ──┘        같은 key면 기존 인스턴스 그대로 반환
```

핵심은 **모델 하나로 통일**했다는 것: STM/MTM/LTM(채팅 사실), doc_rag(문서 청크), graph_rag(엔티티 표기)가 전부 같은 임베딩 공간에 놓여야 서로 다른 저장소를 오가며 코사인 비교(중복 판정, 계층 승급, 퍼지 매칭 등)를 해도 값이 일관된다. 모델을 통일하지 않았다면 저장소마다 벡터 공간이 달라 비교 자체가 성립하지 않는다.

### 근거 — 실측 낭비
호출부 다섯 곳이 서로의 존재를 모른 채 각자 임베더를 만들면, 캐시가 없을 때 한 프로세스에서 같은 모델(arctic-ko)이 3벌 중복으로 올라가 VRAM 8.47GB를 썼고, 그중 4.24GB가 중복이었다. 로딩 시간도 7.2초씩 중복으로 발생했다. 인스턴스가 무상태(모델 가중치 + 디스크 캐시 핸들뿐)라 스레드 간 공유해도 문제가 없다는 점을 확인하고, 호출부를 각각 고치는 대신 factory 레벨에서 캐시 키((backend, model_id, device, batch_size, max_seq_length))로 통제했다.
(`doc_rag/embedding_factory.py`)

## 5. STM/MTM/LTM 분기 구조 — 다른 아키텍처와의 비교

### 현재 상태
`_prefetch_memory()`가 매 턴 STM/MTM/LTM 세 계층을 **전부** 조회한다(계층별 예산 3개씩, `config.memory_tier_budget`). LLM이 판단할 대상이 아니라 무조건 실행되는 전처리 파이프라인이다 — 과거 도구로 뒀다가 절반의 턴에서 건너뛰어져 "아까 그거"류 질문에서 맥락이 빠진 전례가 있어 이렇게 굳힘.

### 다른 아키텍처의 분기 방식 (조사)

| 시스템 | 분기 판단 주체 | 판단 근거 | 우리 스택 적용 가능성 |
|---|---|---|---|
| **Self-RAG** | 모델 자체(파인튜닝) | `[Retrieve]`/`[IsSupported]`/`[IsUseful]` 특수 토큰을 모델이 직접 생성 | 불가 — API 전용 모델은 파인튜닝 불가 |
| **FLARE** | 생성 중 신뢰도 | 토큰 생성 확률이 임계치 밑으로 떨어지는 구간에서만 검색 트리거 | 불가 — OpenRouter API로는 토큰별 로그프롭 미노출 |
| **Adaptive-RAG** | 별도 학습된 분류기 | 질의 복잡도로 "검색 안 함/1단계/다단계" 라우팅 | 가능하나 라벨링된 학습 데이터 필요(비용) |
| **Probing-RAG** | 모델 내부 은닉 상태 프로브 | 은닉층 활성값으로 검색 필요 여부 예측, 검색 57.5% 스킵 | 불가 — 은닉 상태에 API로 접근 불가 |
| **Letta/MemGPT** | 토큰 압박 신호 → LLM 함수 호출 | 프롬프트 토큰이 컨텍스트 70% 넘으면 시스템이 경고 주입, 그 후 LLM이 함수 호출로 판단 | 판단 시점을 정량 신호로 게이트하는 아이디어는 적용 가능 |
| **Generative Agents** | 분기 없음 | recency·importance·relevance 세 점수를 전 메모리에 동일 적용, 단일 랭킹 | 계층 개념 자체가 없어 참고용 |

### 결론 — 우리 스택에 맞는 방향
모델 내부 접근이 필요한 방식(FLARE, Self-RAG, Probing-RAG)은 API 전용 구조상 배제된다. 남는 선택지는 두 갈래다.

1. **점수 하한 필터 (즉시 적용 가능, 추가 비용 0)**: `_search_tier()`가 이미 계산해 둔 코사인 점수에 하한선(예: 0.5)을 두고, 그 밑이면 해당 계층 결과를 프롬프트에서 아예 뺀다. Self-RAG/FLARE/Adaptive-RAG가 공통으로 갖는 "관련성 낮으면 주입 안 함" 게이트를, 이미 있는 값을 재활용해 구현.
2. **소형 분류기/라우터 (Adaptive-RAG식, 별도 비용)**: 질의를 보고 계층별 예산을 조정하는 경량 분류기를 따로 둔다. 라벨 데이터 확보가 선행 조건.

초기 버전은 1번부터 적용하고, 실측(계층별 재현율·프롬프트 길이)으로 2번 필요성을 판단하는 순서를 권한다.
